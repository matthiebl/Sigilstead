# Heartstead — Conventions

Decisions that keep files consistent across sessions. If you break one of these, change it here first.

---

## 1. Identity

| Thing | Value |
|---|---|
| Pack name | **Heartstead** |
| Namespace | `heartstead` |
| Scoreboard/tag prefix | `hs.` |
| Target | Java 26.2, `min_format 107` / `max_format [107, 1]` |

---

## 2. Custom items

Custom items are vanilla items marked with `minecraft:custom_data` under a single `heartstead` key.
**Never** identify a custom item by display name or lore — those are localised and player-editable.

```json
{
  "minecraft:custom_data": {
    "heartstead": {
      "id": "vital_heart",
      "v": 1
    }
  }
}
```

- `id` — snake_case, unique across the pack, matches the item's file name everywhere.
- `v` — schema version for that item. Bump when its stored shape changes so a migration function can
  find old copies.

Predicate for "is this a Vital Heart":

```
items=*[minecraft:custom_data~{heartstead:{id:"vital_heart"}}]
```

Per-item extra state (core attunement target, Vault contents index, tome enchantment) goes **inside**
the same `heartstead` object, never at the root of `custom_data`.

### 2.1 Custom blocks

There are no custom blocks. A "custom block" is a vanilla block + a marker entity or a block-position
entry in `/data storage heartstead:world`. Pick one per system and document it in the system's
function header. Prefer marker entities when the block needs per-tick behaviour, storage entries when
it needs offline accrual (§4.4 of the design wiki).

---

## 3. Function naming

```
heartstead:load                     # minecraft:load tag
heartstead:tick                     # minecraft:tick tag — dispatch only, no logic
heartstead:<system>/<verb>          # public entry points
heartstead:<system>/_<verb>         # internal, leading underscore
heartstead:lib/<util>               # shared helpers, no system may own these
```

Rules:

- `tick.mcfunction` contains **only** scheduled dispatch. Anything doing real work runs from a
  `schedule`d function or a rarer tick gate, never every tick unconditionally.
- One system per directory: `vault/`, `cores/`, `codex/`, `artisan/`, `lives/`, `economy/`,
  `waystone/`.
- Every function starts with a header comment: what it does, what it expects `@s` to be, what
  storage/scores it reads and writes.

---

## 4. Storage layout

All persistent data lives under two roots:

```
heartstead:player   # per-player state, keyed by UUID string
heartstead:world    # world-level state: core registry, waystones, config
```

Nothing else. Do not scatter state across entity NBT unless persistence *requires* it — the one
sanctioned exception is villager `Tags` for taught enchantments (design wiki §7.5), because `Offers`
does not survive restock.

---

## 5. Scoreboards

| Objective | Criterion | Use |
|---|---|---|
| `hs.deaths` | `deathCount` | Lives system |
| `hs.tmp` | `dummy` | Scratch — assume clobbered between functions |
| `hs.cfg.*` | `dummy` | Config values, set in `load` |

Prefix everything `hs.`. Fake-player rows for config use `#hs.<name>` so they never collide with a
real player.

---

## 6. Config

Config is scoreboard values set in `heartstead:load`, overridable by an operator with `/scoreboard`.
Every tuning dial from design wiki §11 must be a config value, not a literal buried in a function.

```
#core_rate_multiplier  hs.cfg.core_rate    100   # percent, 100 = 1.0×
#heart_floor           hs.cfg.heart_floor  5
```

---

## 7. JSON style

- 2-space indent, no trailing commas, LF line endings.
- One resource per file, file name = resource id.
- Generated files carry a `// generated by scripts/<name>.py — do not edit` marker in a
  `heartstead:_meta` key (JSON has no comments), and live in a `generated/` subdirectory.

---

## 8. Resource pack

- Item models use `minecraft:item_model` component pointing at `heartstead:<id>`.
- Every custom item needs a lang key `item.heartstead.<id>` so it is readable **without** the
  resource pack (design wiki §12).
- Textures 16×16 unless there is a reason; keep the source `.xcf`/`.aseprite` out of the pack folder.

---

## 9. Verification

Generated JSON and mcfunction is easy to get *subtly* wrong — condition ordering, and the
`enchantment_level` predicate shape changed in recent versions. Nothing counts as done until it has
been `/reload`ed in the dev world and the behaviour observed. Dialogs need a full world restart.
